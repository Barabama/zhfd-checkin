## 1. 目的与问题陈述

v0.2.0 工程状态的主要产品缺口不是签到状态机或点击安全，而是新机器用户无法从“刚下载程序”顺利走到“确认依赖、看到实例、手动登录、完成 dry-run”：

- 自动发现受安装位置、注册表布局和环境变量限制；找不到自定义路径时，GUI 缺少可浏览兜底；
- 当前错误 TOML 有可见错误提示，但提示后退出，不是 GUI 内修复、验证和恢复；
- 已有页面多而散，新用户不清楚正确操作顺序；
- 安装目录只读、依赖版本冲突和多实例错误缺少统一恢复路径。

本需求的产品目标：**首次配置无需手写 TOML 或打开 PowerShell；当自动发现失败时用户可通过 GUI 选择工具、验证安装并查看实例，配置损坏也能在保留原文件的前提下恢复。**

### 1.2 证据分级与源码对照

需求设计采用以下证据等级，避免把汇总报告中的推断误写成已证实根因：

- **E1 — 汇总直接提供**：run 数量、时间、模式、实例身份、结果字段和 tap 计数；本轮可据此定义产品问题，但仍须独立测试端从原始产物复核。
- **E2 — 截图/日志观察**：用户已逐张查看对应本地截图并报告其显示内容；但图像与采集时间未纳入本分支审计包，故可作为强烈的视觉/route 不一致证据，仍不能独立证明运行时 route，也不能确定 hierarchy 命令失败或 marker 缺失。
- **H — 根因假设**：如动画/WebView 使 UiAutomator 层级不稳定。需由同一 run 的命令退出状态、层级内容、截图和 route 决策共同验证。
- **S — 源码事实**：当前基线源码显示 `adb::AdbDevice::dump_hierarchy()` 先执行 dump，再读取 XML；`locate_or_navigate()` 多处使用 `unwrap_or_default()` 将失败折叠为空 XML，且部分路径以 `navigated` 标志直接赋予 `Checkin` route。`wait_for_package()` 的检查发生在导航流程前，之后的 route 观察没有统一的前台包名快照。

S 级事实说明了为何需要“保留失败类别”和“动作后重新观测”，但不能反向证明附件中的每一次历史 run 都由该代码路径导致；亦不能证明历史 EXE 与当前基线源码一致。原始运行二进制的 provenance 缺失时，归因必须标为未知。

历史运行归因必须核对**产生这些 run 的 EXE 的 `app_version`/`git_commit` 与对应源码**：源码版本与运行二进制可能不是同一构建。当前源码存在层级 dump 错误被 `unwrap_or_default()` 折叠的路径，但需求不预设所有历史 route unknown 都由同一个根因造成；应让层级读取的实际返回状态可观测。

## 2. 用户与使用场景

| 用户/场景 | 需要完成的结果 |
|---|---|
| 新机器首次安装 | 启动后知道下一步，不需要理解内部 CLI 页面结构 |
| 雷电安装在自定义盘符 | 通过文件/目录选择器指定 `ldconsole.exe`，程序发现或允许选择 sibling `adb.exe` |
| 已配置老用户升级 | 原 `config.toml` 和日志保持兼容；升级不静默覆盖用户选择 |
| 多实例操作员 | 能看见 index/name/serial/连接状态，并确认本次 dry-run 范围 |
| 配置损坏用户 | 在 GUI 中看到解析位置、备份原件、修复/重置/取消，并可再次验证 |
| 只读/受限目录用户 | 能看见写权限问题，并选择受支持的数据目录；不得启动后无提示失败 |

## 3. 术语和应用状态

### 3.1 首次使用状态

```text
Welcome
→ DependencyDiscovery
→ DependencySelection
→ DependencyValidation
→ InstanceReview
→ AppReadiness (user signs in manually)
→ DryRunReady
```

向导是可跳过、可重复进入的用户流程，不是运行中的签到业务状态机。向导完成后，普通启动进入工作台；不得每次启动都强制重复向导。

### 3.2 配置状态

```text
ConfigMissing | ConfigInvalid | ConfigReady | ConfigDirty | ConfigSaveFailed
```

配置错误是可恢复 UI 状态。`ConfigInvalid` 时不得用不完整/默认配置继续设备运行。`ConfigDirty` 与磁盘配置分离；没有用户确认不得覆盖磁盘原件。

### 3.3 依赖/设备状态

```text
NotFound | CandidateFound | Selected | ToolValidated | InstanceInventoryLoaded
AdbUnavailable | DeviceOffline | DeviceReady
```

“工具路径有效”“模拟器实例存在”“ADB 设备在线”“目标 App 已登录”是不同事实，不得显示成单一“已连接”。

## 4. 功能需求（P0，v0.3.0 首次使用闭环）

### FR-001 首次启动入口

首次运行发现配置缺失或依赖尚未配置时，GUI MUST 显示引导入口，说明 dry-run 默认行为和手动登录边界，并提供：

1. 扫描依赖；
2. 浏览选择工具；
3. 验证并加载实例；
4. 进入 App 准备说明；
5. 进入工作台 / 执行 dry-run。

向导 MUST NOT 自动登录、自动输入账号/密码/验证码、自动定位、自动签到或改变设备身份。完成状态应持久化或可从配置重建，用户可从导航菜单重新打开向导。

### FR-002 手动选择 LDPlayer / ADB

依赖页 MUST 提供：

- 选择 `ldconsole.exe` 文件入口；
- 选择 ADB 文件入口；
- 当 LDPlayer 已选定时，优先建议同目录 `adb.exe`，但显示候选来源并允许用户更换；
- 显示当前配置路径、候选路径、候选来源、文件是否存在和验证状态；
- 保存前展示将写入的实际路径，支持确认或取消。

选出的任意有效文件路径 MUST 能在自动发现候选为空时作为兜底。路径序列化 MUST 使用合法 TOML 字符串，优先规范化为相对 EXE/data root 的路径或 TOML literal string；不得要求用户手工双写反斜杠。

### FR-003 依赖验证与实例预览

用户选择路径后，可单独执行“验证工具”和“读取实例”：

- LDPlayer 验证至少区分：文件存在、进程可启动/命令执行成功、`list2` 输出可解析；
- ADB 验证至少区分：文件存在、版本命令成功、设备列表获取成功；
- 读取并显示实例 index/name、running、TCP serial 推导/显式 serial、设备几何（如有）及 `ldplayer_reported_port`（仅作为厂商原始报告字段）；
- 验证不得点击 App 或签到按钮；
- 验证失败需显示哪一步失败、原始但适度截断的错误和下一步操作。

结果必须明确区分“工具已验证”“实例已发现”“ADB 设备在线”。发现多个版本时不得静默选择出乎用户预期的工具。

### FR-004 GUI 内配置 Repair

当配置缺失/损坏/不合法时，GUI MUST 进入 Repair/Setup 页面，而不是仅显示提示后结束进程。页面应支持：

- 查看配置文件路径和解析错误行/列（可得时）；
- 打开配置目录或外部编辑器；
- 重新加载磁盘配置；
- 选择其他兼容配置文件；
- 从当前原件生成备份；
- 显式恢复安全默认配置；
- 验证当前编辑内容；
- 应用已验证配置，或取消并回到之前的有效内存配置。

语法错误、字段校验错误、文件权限错误 MUST 区分。恢复默认操作 MUST 二次确认并保留原件备份。不得因解析失败自动重置。

### FR-005 配置事务、备份和回滚

配置保存 MUST 使用同目录临时文件写入、flush/关闭后原子替换；替换前按策略保留一份带时间戳的备份。保存失败时：

- 磁盘上的原始配置保持不变；
- 当前有效内存配置不被半写入值替换；
- GUI 显示失败原因与可操作路径；
- 用户可重新编辑、重试或取消。

配置 reload 时若有后台任务运行，MUST 禁止并发重载，或保证任务使用启动时不可变配置快照。

### FR-006 配置成功后的下一步

依赖配置保存后，界面 MUST 明确显示：已保存哪些工具路径、下一步是读取实例/ADB 连接/用户手动登录/运行 dry-run 中的哪一步。不得只显示泛化“保存成功”。实例页应自动刷新或提供一键刷新，但刷新失败不撤销已保存配置。

### FR-007 只读/受限目录恢复

程序 MUST 在首次写 config/log/report 前识别明显的写入失败，并给出可见提示。产品必须支持一个由用户明确选择的可写 data root；在该决策完成前，不得静默把 config 和用户数据分散到不同目录。

冻结策略：EXE 目录可写时保持便携模式；不可写时由 Setup 明确引导至 `%LOCALAPPDATA%\ZHFDCheckin`。`config.toml`、`logs/`、`captures/`、`reports/`、`backups/` 必须处于同一 data root。CLI 显式 `--config` 优先；有效便携配置优先于已存在的 LocalAppData 配置；无有效便携配置时使用已存在的 LocalAppData root；否则尝试便携 root，可写性检查失败后进入迁移引导。遇到损坏配置不得静默回退或覆盖，必须进入 Repair 并明确显示所选来源。迁移先备份、展示源/目标路径、原子复制并验证；失败保留源配置且不切换 root。

## 5. 功能需求（P1，首次使用后的操作闭环）

### FR-008 有边界的自动发现

继续使用可解释候选源：显式配置、便携目录、环境变量、PATH、注册表/卸载项、有限常见目录。可以增加产品确认过的常见雷电目录模板和有限深度/有限根目录扫描。

MUST NOT 无提示递归扫描所有磁盘。每个候选需显示 source；多个候选可让用户选择；重复/不存在/无权限候选需要有明确表现。手动浏览选择始终作为发现失败兜底。选择 `ldconsole.exe` 后可探测 sibling `adb.exe`，但必须作为可见建议并由用户确认后才能保存。

### FR-009 多实例首次核对

完成实例读取后，用户可在 GUI 逐项核对：index/name/serial/enabled、目标设备在线状态、分辨率/DPI/Profile。首次 dry-run 默认只选第一个 enabled 实例，通常为 index 0；只有用户显式选择全部实例时才运行全实例，并显示预期逐实例运行行为。

一个实例失败 MUST 生成该实例自己的失败结果和日志，不得把该失败冒充其他实例结果。实例专属失败后继续后续实例；公共依赖 preflight 失败则全部计划实例 blocked。存在任何 failed/blocked 时最终退出码非零，并由 GUI 显示 run summary 与逐实例状态。

### FR-010 运行前准备清单

GUI 工作台应呈现清晰顺序：依赖验证 → 实例确认 → Profile 状态 → App 前台/用户已登录（由用户确认或只读检查）→ dry-run。干运行入口可在任何时刻由用户触发，但若有前置问题，需显示已知阻碍。

Live 仍必须走既有 CLI/application 点击策略；向导不可创建 live 授权，也不可将未知签到模式纳入 live。外勤 live 只有在操作员明确设置 `runtime.allow_field_work_live = true` 后才可进入独立的外勤点击路径；它不复用普通模式的业务判断，也仍受全部 Profile、窗口、前台、Ready 和点击前复核门禁保护。

### FR-011 页面层级读取必须可诊断（P0）

页面层级读取 MUST 返回可区分的结果，而不是把失败转为空字符串或等价的 Unknown。候选状态不得授权 live 点击；具体已冻结决策见 `V0.3.0_DECISIONS.md`：

- `dump_succeeded`：成功读取，并记录 UTF-8 是否有效、字节数和耗时；
- `dump_failed`：记录命令/ADB 阶段、可用的退出码/错误类别和经长度限制的 stderr；
- `dump_empty_or_truncated`：读取成功但内容为空或结构不完整；
- `route_markers_missing`：XML 有效，但没有足够页面身份文字；
- `target_app_not_foreground`：当前包名已不是目标 App。

最终机器结果/事件需要保存稳定错误码和恢复建议。每次层级读取 MUST 有唯一 observation/attempt 标识，并记录触发阶段、耗时、命令结果类别、可用退出码、输出字节数、UTF-8/结构校验状态、marker 命中摘要及关联截图/artifact 引用；不得只在整次运行结束时写一个总括状态。调试时 raw hierarchy 是否保留必须是显式可选项，并经过脱敏/长度/保留策略；普通日志默认只记安全摘要和 artifact 引用，避免外发个人或定位信息。截图与 hierarchy 的原始内容只在用户授权的本地 evidence 路径保留，不默认写入可分享的诊断报告。

安全规则仍是：上述情况任何一个都不能单独授权签到点击。hierarchy 不可读时允许有界重试或提示用户手动导航，但不得将 Unknown 静默改为普通 Ready。

### FR-012 路由、视觉与导航动作需要同一时间线（P0）

每次路由决策都应关联同一观察轮次的：前台包名快照、hierarchy 读取状态/marker summary、截图 artifact、页面 route、页面加载阶段、按钮视觉 state 及定位/等待状态。用户和支持者应能够区分“页面实际上不是签到页”“页面 marker 未暴露”“dump 失败”“页面正在加载”“目标页已确认但仍在定位”“visual/hierarchy 证据冲突”。页面身份、页面加载、签到按钮状态和定位状态是不同维度，不得把按钮尚未 Ready 等同 route Unknown。

导航入口 tap、tab tap、swipe、重新 dump、进入签到页复核都 MUST 记录结构化事件：动作类型、步骤编号、动作前 route、目标标签（若来自 hierarchy）、动作后 route/验证结果。不得让 `navigated=true` 成为没有可见审计事件的隐状态。发出导航动作、点击了疑似入口、等待固定时长均不构成页面已到达的证据；动作后 MUST 获取新的页面观察并独立确认 route。若动作后观察失败或证据不足，结果保持 Unknown/候选未确认，不得因“动作已执行”将 route 升格为 Checkin。

若 screenshot 的独立页面证据与 hierarchy 冲突：

- live MUST fail-closed，错误结果使用可区分的 `route_evidence_conflict` 或等价错误码，不能只折叠为泛化 `navigation_not_confirmed`；
- dry-run 可返回“页面候选未确认”的非成功结果，附截图/阶段事件；
- 不得只根据彩色按钮圈、颜色或单一视觉 ready 结果推断 route/mode 并 tap；截图候选只用于诊断展示；正式 route 仍需独立页面身份确认，具体候选与冲突策略遵循 `V0.3.0_DECISIONS.md`。

### FR-013 前台包名在关键状态边界重新确认（P1）

App 启动后检查一次前台包名不足以保证之后一直在目标 App。向导/运行流程 MUST 至少在导航开始、签到状态轮询和 live 点击前记录 package snapshot；在目标 App 已离开前台时返回专门的 `target_app_not_foreground`/`foreground_package_changed` 状态、恢复建议和对应截图引用。

设备查询的失败必须与“成功查询后发现其它包名”区分。Live tap 前的前台包名检查不可移除；此要求不授予自动把 App 拉回前台或重新启动未知页面的权限。

### FR-014 `result.json` 绑定实际构建来源（P1）

每次运行的机器结果 MUST 至少记录产品版本、短 commit/build id 和 `schema_version`。About、CLI version、portable README/ZIP 元数据应能对应到该构建。审计和支持流程 MUST 能识别 release EXE 是否来自当前源码 commit，不能仅从仓库 HEAD 推断一个已经构建的 EXE。

这是针对“运行日志描述某代码行为，但实际执行 EXE 可能来自其他提交”的诊断防护。缺少 provenance 的旧日志应显示 unknown，不能伪造为当前版本。

### FR-015 `--all-instances` 公共阻断与实例结果协调（P1）

当所有实例共享的依赖 preflight（例如 `ldconsole.exe`）失败时，GUI/CLI MUST 明确标记公共原因，避免用户把重复的 3 条同因错误误解成 3 个独立设备故障；同时结果仍需保留各计划实例的 index/name/serial 和 blocked/skipped 状态。不得为减少日志而丢失实例身份。

单一实例专属故障时，其他实例是否继续必须按确认后的级联策略执行；每个实际启动的实例仍保留独立结果目录，最终聚合状态不能覆盖实例级错误。精确策略冻结于 `V0.3.0_DECISIONS.md`：实例专属失败后继续，共享 preflight 失败则全部实例 blocked；只要存在 failed/blocked，聚合退出码非零。
### FR-016 定位中状态与有界等待（P1）

签到页身份、按钮状态和定位状态 MUST 独立建模。视觉/可访问性证据表明已在签到页、但按钮显示“定位中”时，结果应表达 `route=checkin` 与 `button_state=locating`（或等价字段），不得因为按钮未 Ready 将 route 降为 Unknown；该状态绝不授权签到 tap。

处于定位中的轮询 MUST 展示已等待时长、最近状态及停止条件，并按冻结的策略在 Ready、成功/失败终态、前台丢失或等待期限到达时收敛。超过等待期限时须产生明确的 `location_wait_timeout`（或等价）结果，保留最后一轮证据并安全停止；不得静默结束，也不得无限等待。等待上限为 120 秒、轮询周期 2 秒、每 5 秒保存状态证据；窗口剩余不足 5 秒时停止。即使到达 Ready，live 仍须经过全部既有点击授权门禁与稳定帧复核。

## 6. 自动发现策略决策

产品决策：使用“有限自动发现 + 人工文件选择兜底”，不以无界全盘搜索作为成功标准。原因：多版本歧义、权限噪声、性能不可预测以及候选来源难以解释。

新增目录模板应由脱敏的真实安装样本支持，并通过配置覆盖；用户可以不接受自动候选而直接浏览。发现和保存路径不是同一个动作：扫描只展示候选，写配置需用户明确确认。

## 7. 非功能需求

### 可理解性

- 首次操作页面明确写“当前步骤/下一步/需要用户做什么”；
- 错误消息用用户行动导向文案，并保留机器错误码；
- 不要求用户理解 ADB serial、TOML escape、registry 等术语才能完成基本配置。

### 可访问性与布局

- 向导、Repair、实例选择在窄窗和可滚动主内容区仍可操作；
- 长路径可复制且不会挤掉关键操作；
- 中文字体缺失时错误信息仍可通过日志/文本导出读取；
- 对话框不应遮挡唯一恢复路径。

### 隐私与证据

- 不将密码/验证码纳入配置、日志或报告；
- 屏幕截图、hierarchy、绝对路径可能含个人/位置数据，导出前必须说明；
- 结构化报告应继续对 token/通知 URL 做脱敏；
- 日志、备份和恢复报告保存位置与保留策略需明确。

### 可恢复性

- 用户取消任一首次配置步骤，不应破坏现有配置；
- 配置保存、data root 迁移和版本升级都必须可检测失败并回到原状态；
- 用户手动改文件后，GUI reload 成功显示新配置，reload 失败仍保留上次有效内存配置。

## 8. 版本兼容与迁移

- v0.3 MUST 读取 v0.2.0 配置并保留未知/可选字段兼容策略；
- 不得因首次向导而覆盖 `[[emulator.instances]]`、notifications、窗口或已选择工具路径；
- Config schema 如需扩展，采用带默认值的向后兼容字段并记录 schema/config version；
- data root 迁移和升级备份需为显式、可恢复操作；
- 用户取消迁移后继续使用原路径，不对原文件做 destructive mutation。

## 9. 用户旅程验收要求（交由独立测试端）

每个场景需写 Given/When/Then，并提供可复现临时目录/fixture。最低场景：

1. 全新目录 + 常见默认安装被自动发现；
2. 自定义 `E:\leidian\LDPlayer14` 安装未被发现后，文件选择器选中 `ldconsole.exe`，sibling ADB 被建议并验证；
3. 选择错误文件、权限拒绝、工具版本命令失败、`list2` 空/畸形输出；
4. 多候选 LDPlayer 时显示来源并让用户选择，保存前取消不改配置；
5. 选择路径后实例 0/1/2 以正确 index/name/serial 显示，ADB 不在线时状态分层显示；
6. 配置语法错误、缺字段/非法值、UTF-8 读取失败；Repair 内备份、修复、reload、取消、恢复默认、原子保存失败；
7. logs/目录已存在但只读、EXE 在只读目录、data root 迁移中断；
8. 旧 v0.2 config 升级后路径、实例、窗口、通知配置均保留；
9. 向导中用户需手动登录，程序不输凭据、不自动点登录、不点签到；
10. 多实例 dry-run 逐项日志隔离、单实例错误级联和聚合状态符合定义；
11. GUI 在 1024×768、1280×720、125%/150% DPI、长中文路径下仍能修复配置并完成 dry-run 启动准备；
12. 将 9-run 样本事件序列化为 fixture：连续实例启动失败可以归因到共享依赖，已知 root 路由/页面状态仍分别可解释；
13. hierarchy dump 失败、成功但 marker 不存在、空/截断 XML、超时与 stderr 各自得到不同可诊断结果；同一观察轮次可通过 observation/attempt ID 与截图、route 决策关联；对用户报告的 6 张最终截图逐一核对状态分类，截图称为完整签到页/ready、加载 spinner、定位中或桌面时，机器结果应分别提供相符证据或明确冲突原因；
14. 同轮视觉候选 ready 但 route Unknown/证据冲突时，dry-run 有阶段结果、live 零 tap；
15. App 在 `wait_for_package` 后、导航动作后、route 确认前或 live tap 前掉出前台时，结果与普通 `navigation_not_confirmed` 区分，并定位到具体前台检查边界；复现类似 `221102` 的最后截图为模拟器桌面的情况时，不得仅依据先前一次前台检查继续报告 App 页面状态；
16. 每条运行结果的版本/commit 与 About、CLI、便携包构建来源一致；旧结果缺字段显示 unknown；
17. 导航 tap/swipe → 新一轮 hierarchy/screenshot → route transition 的 timeline 能复现从首页到签到页的步骤；仅发出入口 tap 但未能确认目标页时 route 不得成为 Checkin，且不包含未经授权的签到 tap；
18. 用户提供的 6 张最终截图对应场景分别覆盖定位中、按钮 ready、加载 spinner、桌面启动器与成功 dry-run，route 与页面/按钮/定位各状态不能相互冒充；定位等待达到上限时应明确说明停止原因且保持零签到 tap。

## 10. 当前不在本需求范围

- 自动递归搜索整台电脑或所有磁盘；
- 自动安装、下载或升级 LDPlayer / ADB；
- 自动输入学校账号、密码、验证码或自动同意协议；
- 绕过 Profile 标定、时间窗、前台包名、普通业务模式和 Ready 复核；
- 外勤签到 live 点击或 live 计划任务，除非操作员已在当前 data root 中明确启用 `runtime.allow_field_work_live = true` 并完成独立风险确认；
- 以“新用户需求完成”为由对真实设备发起无用户在场的动作。
