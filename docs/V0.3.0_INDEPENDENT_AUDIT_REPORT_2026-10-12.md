## 8. 发现清单（按严重度）

### P0-1 外勤签到（field-work）与普通签到模式门禁完全缺失

- 严重度：P0
- 受影响文件/函数：`rust/src/main.rs::detect_page_route`、`rust/src/main.rs::run_inner_with_device`、`rust/src/main.rs::guarded_tap`、`rust/src/domain.rs::RunResult`
- 复现条件：`cargo test --manifest-path rust/Cargo.toml --lib audit_field_work_page_must_not_be_treated_as_tappable_checkin -- --ignored`
- 实际结果：外勤页 hierarchy（`晚点名签到` + `未签到` + `外勤签到`）被判定为 `PageRoute::Checkin`；断言失败（`left: Checkin, right: Checkin`）。
- 预期结果：外勤页不得进入普通签到 live 路径；live 只能授权 `Checkin + Ordinary`。
- 安全/业务影响：**可能导致未授权/错误位置的点击。** `guarded_tap` 的 `TapRequest` 已不含 `route`/`checkin_mode`，只要按钮视觉连续 2 帧 Ready 且其余门禁满足，live 即可点击外勤页按钮。直接违反 Phase 0 契约 §4.2/§4.5、v0.3 D-08（“不能单独确认 route=checkin 或签到模式”）与长期规则“不把外勤签到误判为普通签到”。
- 建议修复：恢复 `CheckinMode{Ordinary,FieldWork,Unsupported}` 建模；`detect_checkin_mode` 优先识别 `外勤签到`；`guarded_tap` 恢复 `authorize_page_action(route, mode)` 门禁。
- 是否由本轮代码引入：**是**。本分支从 `4cfff0a` 分出，该基线本就没有 `CheckinMode`；v0.3 未继承 v0.2 分支已实现的外勤建模，属能力回退。

### P0-2 live 点击路径不含 route 复核，定位轮询期间不再重新观测页面

- 严重度：P0
- 受影响文件/函数：`rust/src/main.rs::run_inner_with_device`（1378–1573 轮询循环）、`guarded_tap`（1610–1625）、`TapRequest`（1597–1608）
- 复现条件：静态审计 + 现有 dry-run 事件序列；轮询循环只执行 `screenshot + classify_button`，不执行 `dump_hierarchy`，也不重新计算 route。
- 实际结果：route 只在 `locate_or_navigate` 确认一次；`TapRequest` 无 `route` 字段，`guarded_tap` 不校验页面身份。
- 预期结果：Phase 0 契约要求 live tap 必要条件含 `page_route == Checkin AND checkin_mode == Ordinary`；FR-012 要求“动作后必须重新观测”。
- 安全/业务影响：route 确认后、Ready 前的 120 秒内，若 WebView 在同一 App 内跳转到其它页面（前台包名不变），代码仍按签到页处理并可能点击 Ready 元素。
- 建议修复：在轮询循环内按固定节奏重新 dump hierarchy 并复核 route/前台；把 route/mode 重新纳入 `guarded_tap` 授权输入。
- 是否由本轮代码引入：**是**（v0.2 分支的循环内 route 复核与 `authorize_page_action` 未继承）。

### P1-1 `RunResult` 删除 v0.2 既有字段，D-07 兼容性要求未满足

- 严重度：P1
- 受影响文件/函数：`rust/src/domain.rs::RunResult`、`rust/src/main.rs::new_run_result/finalize_run`
- 复现条件：对比 `rust/target/release/logs/.../result.json`（v0.2）与 §5.1 的 v0.3 `result.json`。
- 实际结果：v0.3 结果缺少 `artifact_paths`、`error_stage`、`recovery_action`、`started_at`、`finished_at`、`screen_width/height/dpi`、`page_route`、`checkin_mode`、`checkin_state`、`success_date`、`field_work_ready`。
- 预期结果：D-07 明确要求“保留现有字段并采用向后兼容的可选/默认字段；旧消费者忽略新增字段仍可读取已有字段”。
- 影响：v0.2 消费者读取 v0.3 结果会丢失证据路径与失败阶段；GUI 也无法再展示 `error_stage`/`recovery_action`/`artifact_paths`。旧结果可被 v0.3 解析（`audit_v02_result_json_remains_readable` PASS），但字段被静默丢弃。
- 建议修复：以 `#[serde(default)] Option<...>` 保留 v0.2 字段并标记 deprecated，同时新增 v0.3 字段；schema_version 升到 3 时同步记录迁移说明。
- 是否由本轮代码引入：**是**。

### P1-2 成功语义弱化：绿色按钮即可 `success=true`，无成功文案与日期校验

- 严重度：P1
- 受影响文件/函数：`rust/src/main.rs::run_inner_with_device`（1453–1456、1560–1563）
- 复现条件：真实设备 dry-run 已观察到 `marker_summary="晚点名签到,签到成功"`；代码对 `ButtonState::Success` 直接 `result.success = true` 并 break。
- 实际结果：无 `签到成功/已签到` 文案核对，无 hierarchy 日期与配置时区比对，无 stale/date-unknown 区分。
- 预期结果：Phase 0 §4.4“`success=true` 的语义是本次确认目标日期的签到成功，不能仅因绿色按钮而置 true”。
- 影响：可能把旧的/非当天的成功页面报告为本次成功；`success` 结果不可信。
- 建议修复：恢复成功文案 + 日期（配置时区）三方证据与 `success_stale`/`success_date_unknown` 语义。
- 是否由本轮代码引入：**是**（能力回退）。
